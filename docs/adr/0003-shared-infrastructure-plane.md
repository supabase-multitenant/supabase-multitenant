# ADR-0003 — Shared infrastructure plane, per-tenant databases

**Status:** Accepted — 2026-09-23
**Supersedes:** the fork's inherited "full isolated stack per project" model
**Related:** #103 (host-a-new-app flow), #115 (Coolify template), `deploy/coolify/`

## Context

The purpose of Supabase Multitenant is to reproduce the **Supabase Cloud** operating model on
hardware we own:

> One infrastructure, many isolated databases. The platform is stood up **once**. Each new project
> adds **only a database** and the thin services that must be bound to it.

Supabase deliberately does not open-source its orchestration layer. The official OSS path is to
deploy the self-hosted Supabase compose **per project**, which drags the *whole* stack — gateway,
Studio, pooler, image proxy, and the rest — along with every new project.

Measured on this box, one **idle** project generated by the inherited model:

| Service | RAM (idle) | Bound to one tenant DB? |
|---|---:|---|
| studio | 278.9 MiB | no — talks to `meta` + `api-gw` |
| realtime | 257.6 MiB | **yes** |
| pooler (supavisor) | 253.9 MiB | **no — binds its own `_supabase` metadata DB** |
| storage | 180.2 MiB | **yes** |
| db | 152.4 MiB | **yes — this is the product** |
| meta (postgres-meta) | 111.9 MiB | yes (by default config) |
| functions (edge-runtime) | 103.5 MiB | **yes** |
| imgproxy | 93.8 MiB | no — stateless |
| api-gw (envoy) | 93.8 MiB | no — pure router |
| rest (postgrest) | 51.1 MiB | **yes** |
| auth (gotrue) | 39.7 MiB | **yes** |
| **TOTAL** | **1,616.8 MiB** | **11 containers** |

Extrapolated idle cost of the inherited model: 10 projects → **15.8 GiB / 110 containers**;
50 projects → **78.9 GiB / 550 containers**.

Roughly **half** of every stack is the same infrastructure copied again, and two of the largest
items — the gateway and the admin dashboard — are exactly what the product promises to run once.

## Decision

**Hoist the infrastructure that is not tenant-bound into a single shared plane. A new project
provisions only its database and the services that cannot multiplex.**

### The shared plane — stood up once, never per project

| Service | Why it can be shared |
|---|---|
| **api-gw** (envoy) | pure router, no tenant state; routes by host/path to the tenant's services |
| **supavisor** (pooler) | already binds `/_supabase` — **its own** metadata DB — so one pooler multiplexes every tenant DB |
| **imgproxy** | stateless, no DB |
| **studio** | holds no DB of its own (`STUDIO_PG_META_URL` + `api-gw`); becomes a genuine multi-project dashboard |
| **meta** *(phase 2)* | postgres-meta can address a database per request; requires multi-DB routing |
| **analytics** *(when added)* | shared by construction |

### Per project — provisioned, not copied from a template

| Service | Why it cannot be shared |
|---|---|
| **db** | the tenant's data — the only part that must multiply |
| **auth** (gotrue) | `GOTRUE_DB_DATABASE_URL` binds exactly one database |
| **rest** (postgrest) | `PGRST_DB_URI` binds exactly one database |
| **realtime** | binds one database; state is tied to its WAL/replication slots |
| **storage** | `DATABASE_URL` binds exactly one database (its schema lives in the tenant DB) |
| **functions** | `SUPABASE_DB_URL` binds exactly one database |

This constraint is physical, not a preference: these five services are configured with a single
connection string and have no notion of a tenant selector. Supabase Cloud carries the same
constraint and likewise runs them per project.

### And do not run what a project does not use

A project that uses only Postgres and Auth must not start realtime, storage, edge-runtime,
imgproxy or a studio. Data-plane services are **provisioned on demand** when the project first
enables that capability.

Resulting footprint:

| Configuration | RAM (idle) | Containers |
|---|---:|---:|
| Inherited model, one project | 1,616.8 MiB | 11 |
| Shared plane hoisted | ~896 MiB | 6 |
| DB + Auth only (services on demand) | **~192 MiB** | 2 |

## Consequences

**Positive**

- The two things the product promises to run once — the gateway and the dashboard — run once.
- ~50% lower idle footprint per project, and materially lower again for projects that use a
  subset of the platform.
- Ports, TLS and routing become a property of the shared gateway rather than something allocated
  per project.
- Scales to the number of projects we actually intend to host, on this hardware.

**Negative / accepted cost**

- **This departs from upstream.** SupaPanel/SupaConsole are built as full-stack-per-project; the
  compose generator, the routing layer and the project lifecycle all change. Upstream rebases will
  get harder, and this becomes the defining difference of our fork.
- The shared pooler, gateway and dashboard become **single points of failure** for every tenant.
  They need health checks, restart policy and blast-radius thinking that per-project stacks did
  not require.
- Tenant isolation moves from *structural* to *maintained* for the shared components. A routing
  bug in the gateway or a stray wildcard in Studio is a cross-tenant exposure, not a local fault.
  Every shared-plane change needs a tenant-isolation test.
- Existing projects run the old layout and must be migrated, not left mixed indefinitely.

## Alternatives rejected

- **Keep full stack per project.** Rejected — it is the precise waste this product exists to
  remove. It was never a viable option.
- **Shared Postgres with one schema per tenant.** Rejected earlier by the owner and still
  rejected: it trades away per-tenant database isolation, which is the product.
- **Shared analytics only, everything else per project.** Rejected as insufficient — it leaves the
  gateway and dashboard duplicated, which is the bulk of the cost and the whole point.
- **Kubernetes operator** (`supabase-community/supabase-kubernetes`). Architecturally strong, but
  it requires a second orchestrator beside Coolify, which the owner explicitly ruled out.
